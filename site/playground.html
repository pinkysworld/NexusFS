Playground

Two replicas, one browser tab

A distributed filesystem is easy to describe and hard to believe. This page runs two independent NexusFS replicas locally, so you can partition them, edit both, reconnect, and check for yourself whether they actually agree afterwards.

What is running

The NexusFS core compiled to WebAssembly — the same Rust the native binary runs. Not a mock, not a recording, not a reimplementation in JavaScript. Only the storage backend differs: the daemon writes to an embedded database on disk, this page keeps everything in memory. That substitution is possible because storage is a trait rather than a hard-coded dependency.

Each replica has its own device identity, signing key, operation log, CRDT namespace state and content store. Neither can observe the other except through an explicit sync.

How to use it

  1. Load a scenario, or write to a replica yourself: set a path and content, then press mkdir or put. Directories have to exist before files can go into them.
  2. Compare the state roots. Each replica shows one — a fingerprint of everything it currently holds. Different roots mean the two disagree about the filesystem.
  3. Sync. A → B hands A's operations and content to B. Sync both ways does both directions, as a real session would.
  4. Compare again. Matching roots mean the replicas hold byte-identical filesystems. Sync repeatedly, or in a different order, and the result should not change.

What the numbers mean

State root

A BLAKE3 commitment over every inode and its current content hash. It is a pure function of the operations a replica has applied, so two replicas that agree on it hold identical filesystems. This, not the snapshot head, is what convergence means — the head also carries per-device provenance, so it legitimately differs between replicas holding the same data.

Ops

Entries in the operation log. Each mutation is a signed record of intent rather than a state diff, which is what lets replicas apply them in any order and still land in the same place. Signatures are checked before anything touches state.

Pending

Operations received but not yet applicable — a file whose parent directory has not arrived, or a write whose content is still missing. They are parked and retried automatically rather than rejected, because in an offline-first system arriving early is normal, not an error.

Objects

Everything in the content-addressed store: file chunks, plus the directory and snapshot objects each write produces. Two converged replicas can hold slightly different counts here — snapshots record which device authored them — while still agreeing exactly on the state root.

What to watch for

Nothing is lost to a conflict

Run Name collision: both replicas create /shared while partitioned, each holding a different file. After syncing, both directories survive — one keeps the plain name, the other is renamed with a deterministic suffix. Each replica derives the same suffix independently, so no coordination is required and no writer silently loses work.

Order does not matter

Sync in either direction, repeatedly, in any sequence. Re-applying an operation is a no-op, and operations arriving before their dependencies wait rather than failing. The state root is a function of which operations a replica holds, never of when they turned up.

Operations travel before content

A sync carries the log along with the chunks it references. Chunk hashes are verified on arrival, so a peer cannot substitute different bytes for a hash you asked for. If content is missing, the write parks instead of publishing a file that would fail to read.

Scope

This is the local core, not the network stack

Sync here is a button, not a protocol: the page hands one replica's log and chunks to the other in-process. The QUIC transport, peer handshake and Have/Want negotiation are milestone M3 and do not exist yet. Encryption at rest and proof enforcement are not wired in either. What you are exercising is the state machine those layers will sit on top of.
